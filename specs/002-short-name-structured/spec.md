# Feature Specification: 日志分类与结构化存储

**Feature Branch**: `002-short-name-structured`
**Created**: 2026-04-11
**Status**: Draft
**Input**: User description: "将日志进行分类并且结构化存储到数据库；1：报错信息相同的只保留一条（包含参数不同），不用将所有切分好的存入数据库；2：可以配置忽略结构化保存的报错信息；3：需要相应的页面进行展示；4：其他的你可以进行调研补充"

## Clarifications

### Session 2026-04-11

- Q: 去重判断逻辑 → A: **混合方案**
  - 规则引擎（默认）：用户可编辑规则代码/正则表达式进行文本解析和错误类型匹配
  - AI 模式（可选）：使用 LangChain + Anthropic SDK 调用 AI 阅读切分后日志，输出结构化数据
  - 用户可切换模式，规则引擎为默认快速方案，AI 为复杂场景补充

## User Scenarios & Testing

### User Story 1 - 日志自动分类与存储 (Priority: P1)

开发者和运维人员希望系统能够自动将日志按照错误类型进行分类，并将分类后的日志结构化存储到数据库中，无需手动干预。

**Why this priority**: 这是核心功能，是其他所有功能的基础。没有分类和存储，其他功能都无法实现。

**Independent Test**: 可以通过向系统发送不同类型的日志数据，验证日志是否被正确分类并存储到数据库中。

**Acceptance Scenarios**:

1. **Given** 系统接收到一条错误日志，**When** 日志包含异常堆栈信息，**Then** 系统应将其分类为"异常错误"并存储到数据库
2. **Given** 系统接收到一条普通信息日志，**When** 日志级别为INFO，**Then** 系统应将其分类为"信息日志"并存储到数据库
3. **Given** 系统接收到一条警告日志，**When** 日志级别为WARNING，**Then** 系统应将其分类为"警告日志"并存储到数据库

---

### User Story 2 - 报错信息去重存储 (Priority: P1)

系统应自动识别相同错误消息的日志，即使参数不同也只保留一条记录，避免数据库中存储大量冗余的重复错误信息。

**Why this priority**: 去重是用户明确提出的需求，能显著减少存储空间占用和查询复杂度。

**Independent Test**: 可以向系统发送多条错误消息相同但参数不同的日志，验证数据库中只存在一条该错误类型的记录。

**Acceptance Scenarios**:

1. **Given** 数据库中已存在一条错误日志 "Division by zero"，**When** 系统接收到新日志 "Division by zero (param=1)"，**Then** 数据库中应仍只有一条"Division by zero"记录
2. **Given** 数据库中已存在一条错误日志 "Null pointer at line 10"，**When** 系统接收到新日志 "Null pointer at line 20"，**Then** 数据库中应仍只有一条"Null pointer"记录
3. **Given** 数据库中已存在一条错误日志，**When** 系统接收到完全不同错误消息的日志，**Then** 数据库中应新增一条记录

---

### User Story 3 - 配置忽略规则 (Priority: P2)

管理员应能够配置哪些错误消息不需要进行结构化存储，允许忽略特定的已知无害或频繁出现的错误信息。

**Why this priority**: 这是用户明确要求的功能，允许过滤掉不需要关注的噪音日志。

**Independent Test**: 可以通过配置忽略规则，然后发送符合规则的日志，验证这些日志不会被存储到数据库中。

**Acceptance Scenarios**:

1. **Given** 管理员配置了忽略规则包含"Connection timeout"，**When** 系统接收到错误消息"Connection timeout"的日志，**Then** 该日志不应被存储到数据库
2. **Given** 管理员未配置任何忽略规则，**When** 系统接收到任意错误日志，**Then** 所有日志都应被正常存储
3. **Given** 管理员配置了忽略规则后又删除该规则，**When** 系统接收到之前被忽略的日志，**Then** 该日志应恢复正常存储

---

### User Story 4 - 日志展示页面 (Priority: P2)

用户应能够通过Web页面查看已存储的日志列表，页面应清晰展示日志的关键信息并支持基本导航。

**Why this priority**: 用户明确要求有展示页面才能使用已分类存储的日志。

**Independent Test**: 可以通过浏览器访问日志展示页面，验证页面能够正常加载并显示日志列表。

**Acceptance Scenarios**:

1. **Given** 数据库中存储了多条日志，**When** 用户打开日志展示页面，**Then** 页面应展示日志列表，包含错误消息、分类、时间等信息
2. **Given** 日志数量超过单页显示上限，**When** 用户查看日志列表，**Then** 应支持分页导航
3. **Given** 页面正常加载，**When** 用户查看单条日志详情，**Then** 应展示完整的日志信息包括参数和上下文

---

### User Story 5 - 日志搜索与过滤 (Priority: P3)

用户应能够在日志展示页面通过关键词搜索和条件过滤快速找到需要的日志记录。

**Why this priority**: 随着日志量增长，没有搜索过滤功能的页面将难以使用。

**Independent Test**: 可以通过在页面上输入搜索条件，验证返回的日志列表符合过滤条件。

**Acceptance Scenarios**:

1. **Given** 数据库中存在多条不同类型的日志，**When** 用户输入关键词搜索，**Then** 应返回包含该关键词的日志
2. **Given** 数据库中存在多条日志，**When** 用户按日志分类进行过滤，**Then** 应只返回该分类下的日志
3. **Given** 数据库中存在多条日志，**When** 用户按时间范围进行过滤，**Then** 应只返回该时间范围内的日志

---

### User Story 6 - 日志统计与摘要 (Priority: P3)

系统应提供日志统计功能，帮助用户快速了解错误分布情况和趋势。

**Why this priority**: 调研补充的功能，统计信息能帮助用户快速了解系统健康状况。

**Independent Test**: 可以通过查看统计面板，验证统计数据与实际日志数据一致。

**Acceptance Scenarios**:

1. **Given** 数据库中存储了多日日志，**When** 用户查看统计面板，**Then** 应显示各分类的错误数量分布
2. **Given** 数据库中存储了历史日志，**When** 用户查看趋势图，**Then** 应显示错误数量随时间的变化趋势

---

### Edge Cases

- 当数据库连接失败时，系统应记录错误并提供重试机制，而不是丢失日志数据
- 当收到格式不规范的日志时，系统应能跳过该日志并记录警告，而不是导致整个处理流程中断
- 当忽略规则配置错误导致所有日志都被忽略时，系统应能发出警告提示管理员
- 当去重检测耗时过长时，应有超时机制避免阻塞日志处理流程

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 能够接收并解析多种格式的日志数据
- **FR-002**: 系统 MUST 能够根据日志内容和级别自动进行分类
- **FR-003**: 系统 MUST 能够将分类后的日志结构化存储到数据库
- **FR-004**: 系统 MUST 支持两种去重模式：
  - **规则引擎模式**（默认）：用户可编辑规则代码/正则表达式进行文本解析，判断错误类型是否相同
  - **AI 模式**（可选）：使用 LangChain 调用 AI 阅读日志，输出结构化分析和错误类型判断
- **FR-005**: 系统 MUST 支持配置忽略规则，允许指定哪些错误消息不进行结构化存储
- **FR-006**: 系统 MUST 提供Web页面展示已存储的日志列表
- **FR-007**: 系统 MUST 支持日志列表的分页显示
- **FR-008**: 系统 MUST 支持按关键词搜索日志
- **FR-009**: 系统 MUST 支持按日志分类进行过滤
- **FR-010**: 系统 MUST 支持按时间范围进行过滤
- **FR-011**: 系统 MUST 提供日志统计功能，展示错误分布和趋势
- **FR-012**: 系统 MUST 支持查看单条日志的完整详情
- **FR-013**: 系统 MUST 支持用户编写/编辑规则代码进行文本解析（规则引擎模式）
- **FR-014**: 系统 MUST 支持用户切换规则引擎模式和 AI 模式

### Observability & Diagnostics

- **OBS-001**: 必须记录日志分类操作的开始和结束事件，便于追踪处理流程。
- **OBS-002**: 必须记录去重检测的结果（新增/去重），用于监控去重效果。
- **OBS-003**: 必须记录忽略规则匹配情况，用于审计和规则调整。
- **OBS-004**: 必须记录数据库存储操作的失败情况，便于及时发现存储问题。

### Key Entities

- **LogEntry**: 表示一条已分类的日志记录，包含原始消息、归一化消息、堆栈信息、分类、错误类型、参数、发生时间等字段
- **IgnoreRule**: 表示一个忽略规则，包含规则ID、匹配模式（错误消息关键字或正则表达式）、创建时间、启用状态等字段
- **LogCategory**: 表示日志分类，包含分类ID、分类名称（如"异常错误"、"警告日志"、"信息日志"等）、描述等字段
- **LogStatistics**: 表示日志统计汇总数据，包含统计周期、分类ID、各分类的日志数量等字段
- **ParseRule**: 表示用户编写的解析规则，包含规则ID、规则名称、规则代码/正则表达式、创建时间、启用状态等字段（用于规则引擎模式）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 系统能够在收到日志后5秒内完成分类和存储操作
- **SC-002**: 相同错误消息的日志去重率达到100%，数据库中不存在完全重复的错误记录
- **SC-003**: 管理员配置的忽略规则能够在规则保存后立即生效，无需重启服务
- **SC-004**: 日志展示页面能够在3秒内加载完成，支持显示至少1000条日志记录的分页
- **SC-005**: 搜索和过滤操作能够在2秒内返回结果
- **SC-006**: 统计面板能够准确反映数据库中各分类的实际日志数量
- **SC-007**: 用户能够通过页面清晰区分不同分类的日志，并快速定位问题

## Assumptions

- 日志数据来源于用户上传的日志文件（与 001-log-split 的文件上传功能复用）
- 数据库采用关系型数据库（如PostgreSQL或MySQL）存储结构化日志
- 用户具备基本的计算机操作能力，能够使用Web界面进行日志查询
- 日志量预估在日常使用中每天不超过10万条
- 忽略规则的数量预估在100条以内
- 分类，预估5-8个常见分类足以覆盖大多数场景
- 与 001-log-split 功能解耦，可独立部署使用
- **技术栈**：
  - 后端：Python（复用 001-log-split 技术栈）
  - AI 集成：LangChain + Anthropic SDK（用于 AI 模式下的结构化分析）
  - AI 提供商：
    - **MiniMax-M2.7**（推荐）：通过 `https://api.minimaxi.com/anthropic` 接入，Anthropic API 兼容
    - **OpenRouter**：统一 API 网关，支持多 LLM 提供商
