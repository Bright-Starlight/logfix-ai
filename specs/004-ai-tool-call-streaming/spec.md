## User Scenarios & Testing *(mandatory)*

### User Story 1 - 使用工具调用进行 AI 结构化 (Priority: P1)

用户上传日志文件后，点击"AI 结构化"按钮。系统通过工具调用（Tool Call）方式让 AI 模型对日志进行结构化处理，而不是在提示词中要求模型返回特定格式的 JSON。

**Why this priority**: 工具调用比提示词工程更稳定可靠，能减少因提示词解析失败导致的结构化错误，提升数据质量一致性。

**Independent Test**: 可以通过上传标准日志文件，触发 AI 结构化，验证返回的 JSON 结构是否符合预期格式。

**Acceptance Scenarios**:

1. **Given** 用户已上传日志文件且文件包含有效日志数据，**When** 用户点击"AI 结构化"按钮，**Then** 系统使用工具调用方式发送请求，AI 返回结构化 JSON，数据完整无丢失
2. **Given** 用户已上传日志文件且文件包含无效/空数据，**When** 用户点击"AI 结构化"按钮，**Then** 系统返回友好错误提示，不进行结构化处理
3. **Given** 用户已上传日志文件，**When** AI 结构化过程中模型响应格式错误，**Then** 系统记录错误日志并返回降级提示，提示用户可手动处理

---

### User Story 2 - 流式输出展示结构化进度 (Priority: P1)

用户点击"AI 结构化"后，系统通过 SSE 流式输出实时展示结构化进度和结果，用户能看到数据正在被处理并逐步收到结构化结果，而不是面对静止的界面等待全部完成后一次性显示。

**Why this priority**: 解决 AI 一次性返回全部数据导致的"无进度反馈"问题，提升用户体验，减少用户误以为系统卡死的投诉；同时结构化结果实时推送，无需等待全部处理完成。

**Independent Test**: 可以通过触发结构化操作，观察前端是否实时更新处理进度并逐步收到结构化结果，完成时进度变为 100%。

**Acceptance Scenarios**:

1. **Given** 用户点击了"AI 结构化"按钮，**When** 系统正在处理日志数据，**Then** 前端通过 SSE 实时接收并展示处理进度和结构化结果，用户点击取消后立即中断请求
2. **Given** 结构化处理进行中，**When** 用户关闭页面或切换标签，**Then** 后台继续处理，完成后可在结果列表中查看
3. **Given** 结构化处理进行中，**When** 网络中断或服务重启，**Then** 系统记录中断状态，用户重新进入时可继续或重新开始

---

### User Story 3 - 模型预加载与复用 (Priority: P2)

系统启动时预加载 AI 模型（类似单例模式），而非每次调用时临时加载。模型常驻内存，保证结构化请求的快速响应。

**Why this priority**: 减少模型加载延迟，提升结构化响应速度；同时降低因频繁创建模型导致的资源消耗和内存碎片化。

**Independent Test**: 可以通过查看系统日志确认模型在启动时被加载（而非首次调用时），并通过多次调用验证模型实例被复用。

**Acceptance Scenarios**:

1. **Given** 系统启动完成，**When** 尚未有任何用户发起结构化请求，**Then** AI 模型已预加载并处于就绪状态，日志记录"模型预加载完成"
2. **Given** 系统已有活跃模型实例，**When** 用户发起结构化请求，**Then** 直接使用已加载模型处理请求，无需等待模型加载
3. **Given** AI 模型加载失败（如 API Key 无效、模型服务不可达），**When** 用户发起结构化请求，**Then** 系统返回明确错误提示，提示检查配置而非卡住等待

---

### User Story 4 - Token 消耗调研与优化 (Priority: P3)

针对工具调用 vs 提示词工程两种方式的 token 消耗进行对比调研，确保在稳定性和成本之间找到最优解。

**Why this priority**: 工具调用可能增加 token 消耗，需要在正式实施前评估成本影响，避免线上账单超出预期。

**Independent Test**: 可以通过对比相同日志数据分别使用两种方式的 token 消耗，计算成本差异。

**Acceptance Scenarios**:

1. **Given** 相同的日志测试数据集，**When** 分别使用提示词工程和工具调用进行结构化，**Then** 系统记录两种方式的 token 消耗，可生成对比报告
2. **Given** Token 消耗对比报告，**When** 工具调用成本显著高于提示词工程（如超过 20%），**Then** 提供成本分析和建议，决定是否采用工具调用

---

### Edge Cases

- AI 模型服务不可用或超时：系统应记录详细错误日志，返回用户友好提示，不暴露内部错误细节
- 日志数据量极大（如超过 10 万条）：需要分批处理，每批 100 条，前端实时展示批次进度
- 结构化结果格式异常（如缺少必要字段）：系统应记录原始输入和输出，提供手动修复入口
- 并发多个结构化请求：使用 Semaphore 控制并发（默认 5），避免触发 RPM 限制
- 用户关闭页面或切换标签：后台继续处理，完成后可结果列表查看

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持通过工具调用（Tool Call）方式调用 AI 模型进行日志结构化，而非仅依赖提示词工程
- **FR-002**: AI 结构化过程 MUST 通过 SSE (Server-Sent Events) 实时推送处理进度和结构化结果，前端动态更新进度条并逐步展示结果
- **FR-003**: AI 模型 MUST 在系统启动时预加载，预加载完成后记录日志；模型实例应被复用而非每次调用新建
- **FR-004**: 用户 MUST 可在结构化过程中取消操作，取消后立即中断请求
- **FR-005**: 系统 MUST 记录结构化过程的详细日志，包括开始时间、结束时间、处理条数、异常信息
- **FR-006**: 工具调用与提示词工程两种方式的 token 消耗 MUST 可对比统计，用于成本分析

### Observability & Diagnostics *(mandatory if feature changes runtime behavior)*

- **OBS-001**: 记录模型预加载事件（开始/成功/失败），包含加载耗时和模型标识
- **OBS-002**: 记录每个结构化请求的输入数据量（条数/字节）、输出结果大小、token 消耗、耗时
- **OBS-003**: 流式推送失败或中断时，记录断开原因和时间点
- **OBS-004**: 日志文件命名：`logfix-ai_YYYYMMDD.log`，输出到 `/log` 目录

### Key Entities *(include if feature involves data)*

- **LogEntry**: 日志条目，包含原始消息、时间戳、级别等属性
- **StructuredResult**: 结构化结果，包含分类标签、关键字段提取、原始引用等
- **ClassificationSession**: 分类会话，记录会话状态、进度、关联的日志条目、user_id 等
- **TokenUsage**: Token 消耗记录，包含 user_id 用于分用户统计

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户点击"AI 结构化"后，进度条实时更新，延迟不超过 500ms；结构化结果实时推送，无需等待全部完成
- **SC-002**: 模型预加载后，首次结构化请求的响应时间比预热（无预加载）快 80% 以上
- **SC-003**: 工具调用结构化的成功率（返回有效 JSON 比例）达到 99% 以上
- **SC-004**: 系统可记录并展示 token 消耗对比数据
- **SC-005**: 关键流程（模型加载、结构化请求、流式推送）均可通过日志追踪输入、分支与结果

## Assumptions

- AI 模型服务（MiniMax 或其他）支持工具调用（Tool Call）功能和流式输出（streaming）
- 现有系统架构支持在启动时执行初始化任务（类似 ApplicationRunner 或生命周期钩子）
- 模型为单例实例，使用 `asyncio.Semaphore` 控制并发（默认 5 并发，付费用户留 30% 余量），批次处理提高 TPM 利用率
- Token 消耗通过 OpenAI SDK 响应获取（`usage` 字段），支持 `input_tokens` 和 `output_tokens` 统计
