## User Scenarios & Testing *(mandatory)*

### User Story 1 - 完整日志分析流程 (Priority: P1)

用户需要完成从文件上传到分类存储的完整日志分析流程，在切分完成后选择分类模式（规则引擎或AI），系统自动完成分类、去重、忽略规则过滤，最终存储结构化数据并可通过页面查看。

**Why this priority**: 这是本功能的核心集成场景，将001的文件切分与002的分类存储串联成完整工作流。

**Independent Test**: 可以通过上传已知内容的日志文件，执行切分，选择分类模式，验证分类存储结果和页面展示是否正确。

**Acceptance Scenarios**:

1. **Given** 用户上传了一个包含多种错误类型的日志文件，**When** 用户完成切分并选择"规则引擎"模式，**Then** 系统按规则引擎分类去重后存储，用户可在日志列表页面看到分类后的日志
2. **Given** 用户上传了一个包含多种错误类型的日志文件，**When** 用户完成切分并选择"AI模式"，**Then** 系统调用AI分析分类去重后存储，用户可在日志列表页面看到分类后的日志
3. **Given** 用户已完成切分，**When** 用户切换分类模式，**Then** 系统重新执行分类流程并更新存储结果
4. **Given** 用户上传文件后未执行切分，**Then** 系统不显示分类模式选择

---

### User Story 2 - 切分结果直接分类 (Priority: P1)

用户在完成文件切分后，无需额外操作即可将切分结果送入分类流程，实现一键式日志分析。

**Why this priority**: 简化操作步骤，提升用户体验，避免用户在切分和分类之间需要手动衔接。

**Independent Test**: 可以通过执行切分后验证切分结果片段是否自动进入分类队列。

**Acceptance Scenarios**:

1. **Given** 用户完成日志文件切分，**When** 切分状态变为已完成，**Then** 系统自动显示分类模式选择界面
2. **Given** 用户选择分类模式后，**When** 分类处理完成，**Then** 系统显示处理结果摘要（分类数量、去重数量、存储数量）
3. **Given** 分类过程中，**When** 用户关闭或刷新页面，**Then** 后端保存分类进度，用户返回后可继续查看结果

---

### User Story 2.1 - 后台处理进度显示 (Priority: P1)

分类处理为耗时的后台任务，用户需要实时看到处理进度，包括当前处理位置、总数量、处理阶段和预估剩余时间。

**Why this priority**: 后台处理用户无法感知进度，需要进度条让用户知道系统正在工作，避免误以为页面卡死而刷新导致重复提交。

**Independent Test**: 可以通过启动分类处理后观察进度条是否实时更新，并在页面刷新后是否恢复进度显示。

**Acceptance Scenarios**:

1. **Given** 用户选择了分类模式并启动处理，**When** 后台开始处理，**Then** 系统显示进度条，包含百分比和当前处理位置
2. **Given** 分类处理正在进行中，**When** 后台完成一个处理阶段（如去重、分类、存储），**Then** 进度条更新显示当前阶段名称
3. **Given** 分类处理正在进行中，**When** 后台处理了部分日志，**Then** 进度条实时更新百分比和预估剩余时间
4. **Given** 分类处理正在进行中，**When** 用户刷新页面，**Then** 进度条恢复显示当前实际进度，而非从头开始
5. **Given** 分类处理完成，**When** 后台返回处理结果，**Then** 进度条显示100%并显示处理结果摘要

---

### User Story 3 - 分类结果页面查看 (Priority: P2)

用户需要查看已存储的分类日志列表，支持按关键词、分类类型、时间范围搜索过滤。

**Why this priority**: 用户完成日志分析后需要查看和检索结果，是002的核心展示功能。

**Independent Test**: 可以通过上传日志、执行切分分类后，在日志列表页面验证搜索过滤功能是否正常。

**Acceptance Scenarios**:

1. **Given** 数据库中存储了多条分类日志，**When** 用户打开日志列表页面，**Then** 页面展示日志列表，包含错误消息摘要、分类、时间等信息
2. **Given** 日志数量超过单页显示上限，**When** 用户查看日志列表，**Then** 应支持分页导航
3. **Given** 数据库中存在多条不同类型的日志，**When** 用户输入关键词搜索，**Then** 返回包含该关键词的日志
4. **Given** 数据库中存在多条日志，**When** 用户按日志分类进行过滤，**Then** 只返回该分类下的日志
5. **Given** 数据库中存在多条日志，**When** 用户按时间范围进行过滤，**Then** 只返回该时间范围内的日志

---

### User Story 4 - 忽略规则配置 (Priority: P2)

管理员需要配置忽略规则，过滤掉不需要存储的日志类型（如已知无害的连接超时信息）。

**Why this priority**: 002明确要求的功能，允许用户过滤噪音日志。

**Independent Test**: 可以通过配置忽略规则后上传相关日志，验证被忽略的日志不会被存储。

**Acceptance Scenarios**:

1. **Given** 管理员配置了忽略规则包含"Connection timeout"，**When** 系统接收到错误消息"Connection timeout"的日志，**Then** 该日志不被存储到数据库
2. **Given** 管理员配置了忽略规则后又删除该规则，**When** 系统接收到之前被忽略的日志，**Then** 该日志恢复正常存储
3. **Given** 忽略规则配置保存后，**When** 用户上传新日志并执行分类，**Then** 新规则立即生效，无需重启服务

---

### User Story 5 - 分类统计概览 (Priority: P3)

系统提供分类统计功能，帮助用户快速了解日志分布情况。

**Why this priority**: 调研补充的功能，帮助用户快速了解系统健康状况。

**Independent Test**: 可以通过查看统计面板，验证统计数据与实际日志数据一致。

**Acceptance Scenarios**:

1. **Given** 数据库中存储了多日的日志，**When** 用户查看统计面板，**Then** 应显示各分类的错误数量分布
2. **Given** 数据库中存储了历史日志，**When** 用户查看趋势视图，**Then** 应显示错误数量随时间的变化趋势

---

### Edge Cases

- 切分完成但分类模式选择前页面关闭：**后端保存切分结果和待分类状态，用户返回后可继续**
- AI模式处理失败：**当AI服务不可用或调用超时时，系统提示用户"AI服务暂时不可用，请选择规则引擎模式"，用户手动切换到规则引擎模式继续处理**
- 忽略规则配置错误导致所有日志被忽略：**系统发出警告提示管理员**
- 数据库连接失败：**记录错误并提供重试机制，保留待处理数据**
- 分类处理耗时过长：**显示进度指示器，支持后台处理**
- 切分结果为空：**提示用户检查切分规则是否正确**

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须允许用户上传本地文本日志文件（.log, .txt, .json等常见格式）
- **FR-002**: 系统必须在文件上传后显示文件内容预览（默认前100行）
- **FR-003**: 系统必须支持正则表达式和固定分隔符作为切分规则
- **FR-004**: 系统必须在切分完成后展示切分结果列表
- **FR-005**: 系统必须在切分完成后自动显示分类模式选择界面（规则引擎/AI模式）
- **FR-006**: 系统必须支持用户切换分类模式（规则引擎模式和AI模式）
- **FR-007**: 系统必须支持规则引擎模式分类：用户可编辑解析规则代码/正则表达式进行文本解析
- **FR-008**: 系统必须支持AI模式分类：使用LangChain调用AI阅读切分后日志，输出结构化分析
- **FR-009**: 系统必须在分类前执行去重：相同错误消息的日志（参数不同）只保留一条
  - 去重判断标准：归一化后的错误消息（已去除时间戳、动态参数等变量部分）完全一致，判定为重复
  - 具体实现逻辑参见002功能规格 `specs/002-classification-storage/spec.md` 中的去重算法定义
- **FR-010**: 系统必须在分类前执行忽略规则过滤：符合忽略规则的日志不进行存储
  - 规则匹配方式：多条忽略规则之间为OR关系，任一规则匹配即触发忽略
  - 规则匹配逻辑：正则匹配原始错误消息，支持通配符
- **FR-011**: 系统必须将分类后的日志结构化存储到数据库
- **FR-012**: 系统必须提供Web页面展示已存储的日志列表
- **FR-013**: 系统必须支持日志列表的分页显示
- **FR-014**: 系统必须支持按关键词搜索日志
- **FR-015**: 系统必须支持按日志分类进行过滤
- **FR-016**: 系统必须支持按时间范围进行过滤
- **FR-017**: 系统必须支持查看单条日志的完整详情
- **FR-018**: 系统必须提供日志统计功能，展示分类分布和趋势
- **FR-019**: 系统必须在分类操作完成后记录处理结果摘要（分类数量、去重数量、存储数量）
- **FR-020**: 系统必须在切分状态完成后自动进入分类流程，无需用户手动触发
- **FR-021**: 系统必须支持分类模式切换后重新执行分类
- **FR-022**: 系统必须在分类处理过程中显示进度条，包含当前处理位置百分比
  - 进度百分比计算基准：已处理数量 / 切分片段总数（total_items）× 100
- **FR-023**: 系统必须在分类处理过程中显示当前处理阶段名称（如"去重检测中"、"分类分析中"、"存储中"）
- **FR-024**: 系统必须在分类处理过程中显示预估剩余时间
- **FR-025**: 系统必须在分类处理过程中实时更新进度（更新间隔不超过2秒）
- **FR-026**: 系统必须支持刷新页面后恢复进度显示，而非从头开始
- **FR-027**: 前端必须每2秒轮询一次 `GET /api/classification/{session_id}/progress` 获取最新进度（见FR-025）

### Observability & Diagnostics *(mandatory if feature changes runtime behavior)*

- **OBS-001**: 必须记录文件上传事件，包含文件名、文件大小、上传时间
- **OBS-002**: 必须记录切分规则应用事件，包含规则类型、规则内容、匹配数量
- **OBS-003**: 必须记录分类模式选择事件，包含所选模式（规则引擎/AI）
- **OBS-004**: 必须记录分类处理结果，包含分类数量、去重数量、被忽略数量、存储数量
- **OBS-005**: 必须记录去重检测结果（新增/去重），用于监控去重效果
- **OBS-006**: 必须记录忽略规则匹配情况，用于审计和规则调整
- **OBS-007**: 必须记录错误事件，包含错误类型、错误消息、操作上下文
- **OBS-008**: 必须记录进度更新事件，包含当前阶段、已处理数量、总数量（用于性能分析）
- **OBS-009**: 日志文件命名规范为 `logfix-ai_{日期}.log`，例如 `logfix-ai_20260411.log`

### Key Entities *(include if feature involves data)*

- **LogFile**: 上传的日志文件，包含文件名、文件大小、编码、原始内容、存储路径（来自001）
- **SplitRule**: 切分规则，包含规则类型（regex/fixed-string）、规则内容、规则名称（来自001）
- **SplitResult**: 切分结果，包含片段序号、起始行号、结束行号、片段内容（来自001）
- **SplitSession**: 切分会话，关联LogFile与多个SplitResult，包含会话ID、状态、创建时间（来自001）
- **LogEntry**: 表示一条已分类的日志记录，包含原始消息、归一化消息、分类、错误类型、参数、发生时间等字段（来自002）
- **IgnoreRule**: 表示一个忽略规则，包含规则ID、匹配模式、创建时间、启用状态等字段（来自002）
- **ParseRule**: 表示用户编写的解析规则，包含规则ID、规则名称、规则代码/正则表达式、启用状态等字段（来自002）
- **ClassificationSession**: 分类会话，关联SplitSession与分类结果，包含会话ID、所选分类模式、状态、创建时间
- **ClassificationProgress**: 分类进度，包含会话ID、状态（等待中/处理中/已完成/失败）、已处理数量、总数量、当前阶段名称、预估剩余时间、最后更新时间

### Data Flow

```
[文件上传]
    ↓
[文件切分] ← 规则配置（正则/分隔符）
    ↓
[切分结果片段]
    ↓
[分类模式选择] ← 用户选择：规则引擎 / AI模式
    ↓
[分类处理] ← 后台执行，进度实时上报
    ├→ [去重检测]
    ├→ [忽略规则过滤]
    ├→ [分类分析]
    └→ [存储]
    ↓
[结构化存储]
    ↓
[分类结果展示]
```

### Progress Tracking API

- **PT-001**: `GET /api/classification/{session_id}/progress` 返回当前分类进度，包含已处理数量、总数量、当前阶段、预估剩余时间
- **PT-002**: 进度更新通过轮询机制获取，前端每2秒请求一次（见FR-025）
- **PT-003**: 进度状态枚举：`PENDING`（等待中）、`PROCESSING`（处理中）、`COMPLETED`（已完成）、`FAILED`（失败）

### Integration Points

- **IP-001**: 001的日志文件上传组件直接复用，作为整个流程的入口
- **IP-002**: 001的切分规则配置和执行逻辑直接复用
- **IP-003**: 001的切分结果展示组件直接复用
- **IP-004**: 002的分类模式选择UI在本功能中作为切分完成后的引导界面
- **IP-005**: 002的分类处理逻辑（规则引擎和AI模式）直接复用
- **IP-006**: 002的去重和忽略规则逻辑直接复用
- **IP-007**: 002的日志列表展示页面直接复用，作为分类结果的查看入口
- **IP-008**: 002的忽略规则配置页面直接复用

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以在120秒内完成从上传文件到查看分类结果的全流程
- **SC-002**: 相同错误消息的日志去重率达到100%，数据库中不存在完全重复的错误记录
- **SC-003**: 管理员配置的忽略规则能够在规则保存后立即生效，无需重启服务
- **SC-004**: 日志展示页面能够在3秒内加载完成，支持显示至少1000条日志记录的分页
- **SC-005**: 搜索和过滤操作能够在2秒内返回结果
- **SC-006**: 规则引擎模式分类处理1000条日志的时间不超过10秒
- **SC-007**: AI模式分类处理每条日志的平均响应时间不超过5秒（含AI调用延迟）
- **SC-008**: 所有关键操作都记录到日志文件，可追溯操作历史
- **SC-009**: 分类模式切换后，系统能够在30秒内完成重新分类并更新结果
- **SC-010**: 进度条更新延迟不超过2秒，用户能实时感知处理进度
- **SC-011**: 进度百分比准确度达到100%，进度条能正确反映实际处理完成比例

## Assumptions

- 001和002的功能模块已实现并通过测试
- 001的切分结果格式与002的分类输入格式兼容
- AI模式使用MiniMax-M2.7或OpenRouter作为AI提供商
- 数据库采用PostgreSQL存储结构化日志（复用002技术栈）
- 后端采用Python实现（复用001和002技术栈）
- 前端采用React实现（复用001和002技术栈）
- 分类会话与切分会话关联，支持按来源文件追溯
- 用户熟悉基本的正则表达式语法
- 系统运行在Windows环境
