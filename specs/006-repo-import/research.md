# 研究: 仓库导入功能

**Branch**: `006-repo-import` | **Date**: 2026-04-12

## 研究结论

本特性为现有架构的简单扩展，无需深度研究。

## 技术决策

### 决策 1: 本地仓库验证方式

**选择**: 直接检查 `.git` 目录存在性

**理由**:
- 现有应用运行在用户本地机器，无需通过网络验证
- 性能最优：O(1) 文件系统操作
- 可靠：`.git` 目录是 Git 仓库的充分必要条件

**替代方案考虑**:
- 执行 `git rev-parse --git-dir`: 更准确但需要 Git CLI 存在
- 直接采用 `.git` 目录检查足够满足需求

### 决策 2: GitHub 仓库验证方式

**选择**: 仅发送 HEAD 请求验证存在性，不获取完整数据

**理由**:
- HEAD 请求开销最小（不下载仓库内容）
- 10 秒超时足够应对正常网络
- 公开仓库无需认证即可验证

**替代方案考虑**:
- 使用 GitHub REST API (`GET /repos/{owner}/{repo}`): 返回更丰富信息但多一次 API 调用
- 使用 GitHub GraphQL API: 更灵活但复杂度高
- 初版保持简单，验证存在性即可；描述等信息在导入时获取

### 决策 3: 会话状态存储

**选择**: 存储在 PostgreSQL 中（与其他实体一致）

**理由**:
- 符合现有数据存储模式
- 支持后续扩展（导入历史、收藏等）
- 便于审计和可追溯性

**不采用方案**:
- 前端 localStorage: 不够可靠（可被清除、无法跨设备）
- Redis: 增加部署复杂度，初版不需要高性能
