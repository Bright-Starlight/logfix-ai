# RepoInsight Constitution

## Core Principles

### I. 规范驱动开发

每个功能都从完整的规格说明开始。功能规格必须包含可独立测试的用户场景。规格必须在编码前获得批准。理由：防止对错误实现浪费精力；提供明确的验收标准。

### II. TDD（测试驱动开发）（不可妥协）

代码开发必须遵循 TDD。先写测试，测试必须初始失败，实现后测试通过。必须严格遵循 Red-Green-Refactor 循环。理由：确保可测试性、防止回归、在假设之前验证。

### III. 增量交付

功能必须能够以独立增量方式交付。每个用户故事必须可独立测试和部署。必须遵循 MVP 优先原则——先实现最简可行方案。理由：降低风险、提前获得反馈、防止过度设计。

### IV. 代码质量

代码必须清晰、可读、命名良好。函数应小（50 行以内），文件应专注（800 行以内）。优先使用不可变性；必须明确且受控地使用可变操作。错误必须在每一层全面处理。必须保留有意义的注释，不得随意删除注释。理由：可维护性、可调试性、减少副作用。

### V. 可观测性

所有重要操作必须通过结构化日志可观测。必须使用文本 I/O 协议进行调试（stdin/stdout/stderr）。理由：支持生产环境调试、事件响应和性能分析，无需专用工具。

### VI. 文档语言

项目所有文档正文内容必须使用中文编写。模板标题（如 "User Scenarios & Testing"、"Functional Requirements"）可保留英文作为标准化标记，但生成的规格说明、计划文档等正文必须使用中文。理由：确保团队所有成员可理解项目文档，避免语言障碍导致的误解。

**报告与总结语言**：所有完成后的报告、总结、审查意见等输出内容一律使用中文编写，包括但不限于 `/speckit.implement` 完成报告、代码审查报告、测试报告等。

### VII. 代码执行流程图

在 `/speckit.tasks` 阶段（实现前），必须画出代码执行流程图并保存到 `specs/###-feature-name/flow.md`，使用 **Mermaid 语法**。**流程图中的所有文字内容必须使用中文编写**，包括节点描述、状态名称、函数说明等。理由：代码实现前明确运行时事件流和数据流，减少返工风险；确保团队所有成员可理解流程图，避免语言障碍导致的误解。

### VIII. 集成验证

在 `/speckit.implement` 完成后，必须验证功能已正确集成到主应用中，而非仅完成独立模块开发。验证方式：

1. **代码层面验证（必须）**：直接在代码中检查以下内容：
   - 组件是否已导入到主应用（如 App.tsx）
   - 组件是否正确渲染（传递正确的 props）
   - Store 状态是否正确连接
   - 用户可见功能入口是否存在
   - UI 组件是否实际使用了 store 中的数据

2. **清单文件验证（辅助）**：检查清单文件的完成状态

验证必须通过阅读代码确认，而非仅依赖清单文件打勾。理由：防止功能开发完成后因未集成而导致用户无法使用，之前问题（如 MetadataPanel 未集成到 App.tsx、进度显示未实现）表明这一步骤的必要性。

## Additional Constraints

### 安全要求

- 不得硬编码密钥（API 密钥、密码、令牌）——必须使用环境变量或密钥管理器。
- 所有用户输入必须在处理前验证。
- 遇到无效输入时必须快速失败并给出清晰的错误信息。
- 理由：防止凭证泄露和注入攻击。

### 性能标准

- 必须在功能计划中定义性能目标（如吞吐量、延迟、资源限制）。
- 关键路径应包含性能测试。
- 理由：防止生产环境性能退化。

### Windows 环境

当前开发环境为 Windows。代码和脚本必须兼容 Windows 平台。理由：确保开发人员在 Windows 环境下正常工作，所有工具链和脚本应在 Windows 上可执行。

## Development Workflow

### 流程要求

1. **先研究**：编码前先搜索现有实现、模板和模式。
2. **先计划**：编码前必须创建并审查实施计划。
3. **先测试**：遵循测试驱动开发原则。
4. **代码审查**：所有变更在合并前必须审查；审查者必须验证宪法合规性。
5. **宪法合规**：所有 PR 和审查必须验证对本宪法的遵循。偏离宪法原则时必须在计划文档中说明理由。

### 质量门禁

- 功能实现仅在规格批准后开始。
- 用户故事实现仅在基础阶段完成后开始。
- 测试必须通过后方可合并。
- 计划模板中的宪法检查必须在 0 阶段研究开始前通过。

## Governance

本宪法优先于所有其他开发实践。修正必须遵循以下程序：

1. 提议的变更必须记录理由和迁移计划。
2. 变更必须通过与代码变更相同的审查流程批准。
3. 版本号必须遵循语义化版本规则递增：
   - MAJOR：向后不兼容的治理变更、原则移除或重新定义。
   - MINOR：新原则、新章节或实质性扩展的指导。
   - PATCH：澄清、措辞修正、错别字纠正、非语义性改进。
