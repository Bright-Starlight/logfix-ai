# LogFix AI MVP 小需求拆解

本文将 MVP 拆成适合直接进入开发的最小需求单元。考虑到过细拆分会增加协作成本，当前推荐以“单次会话可完成的工作包”为主，而不是每个点都独立成卡。

## 推荐会话级工作包

1. WP-01 基础骨架、上传与解析
2. WP-02 异常聚合与基础界面
3. WP-03 本地仓库接入与代码检索
4. WP-04 AI 分析与修复任务生成
5. WP-05 可用性增强

## P0-1 项目骨架与基础配置

### 目标

建立一个可运行的本地应用骨架，确保后续模块可以持续叠加。

### 小需求

1. 初始化后端项目结构
2. 初始化服务端 Web 展示结构
3. 配置本地开发环境与 `.env` 示例
4. 配置 SQLite 数据目录和仓库目录
5. 提供基础启动脚本和健康检查接口

### 验收标准

- 本地可一条命令启动
- 页面可访问
- 数据目录自动创建
- 健康检查接口返回正常

## P0-2 日志上传

### 目标

让用户能稳定上传单个或多个日志文件。

### 小需求

1. 支持拖拽上传日志文件
2. 支持选择多个文件上传
3. 校验文件大小和后缀
4. 将原始文件保存到本地工作目录
5. 记录一次上传任务的元信息

### 输入

- `.log`
- `.txt`
- `.json`
- `.zip`

### 输出

- 上传任务记录
- 原始文件路径

### 验收标准

- 支持 10MB 内文件上传
- 批量上传至少支持 5 个文件
- 非法文件类型能提示失败原因

## P0-3 日志解析

### 目标

将原始日志转为可查询的结构化记录。

### 小需求

1. 设计统一日志记录字段
2. 实现常见文本日志按行解析
3. 实现 JSON 日志解析
4. 提取时间、级别、消息、堆栈等字段
5. 对无法完整解析的行保留原文
6. 保存解析结果到 SQLite

### 建议字段

- `id`
- `upload_id`
- `source_file`
- `timestamp`
- `level`
- `service`
- `module`
- `message`
- `stack_trace`
- `trace_id`
- `raw_text`
- `parse_status`

### 验收标准

- 能处理常见文本日志和 JSON 日志
- 解析失败的日志不会丢失
- 原始文本可追溯

## P0-4 异常聚合

### 目标

将大量日志归并成便于排查的异常组。

### 小需求

1. 设计错误指纹生成规则
2. 根据 message 与 stack trace 聚合
3. 计算异常组次数、首次出现、最后出现
4. 为异常组选取代表样本
5. 提供严重度映射规则

### 输出

- 异常组表
- 异常组与日志记录的关联表

### 验收标准

- 同类错误能合并
- 列表页能展示聚合后的异常组
- 可查看异常组下的原始日志样本

## P0-5 异常列表与详情页

### 目标

提供最基础但可用的排障浏览界面。

### 小需求

1. 展示异常组列表
2. 支持按时间、级别、服务过滤
3. 支持关键词搜索
4. 展示异常组详情
5. 展示原始日志样本和聚合摘要

### 验收标准

- 用户能在列表页快速找到主要异常
- 用户能进入详情页查看样本与统计信息

## P0-6 Git 仓库导入

### 目标

为日志分析建立代码上下文基础。

### 小需求

1. 选择本地仓库目录
2. 校验目录是否为可用代码仓库
3. 记录仓库名称和本地路径
4. 对目录读取失败给出清晰提示

### 验收标准

- 成功接入至少一个本地代码仓库
- 后台可记录仓库状态
- 目录重载操作可重复执行

## P0-7 代码切分与索引

### 目标

将代码库转为可检索的上下文片段。

### 小需求

1. 扫描仓库文件
2. 过滤二进制和无关目录
3. 先按文件级建立索引
4. 可选补充函数级切分
5. 保存索引元数据

### 元数据建议

- `repo_id`
- `file_path`
- `symbol_name`
- `chunk_type`
- `content`
- `language`

### 验收标准

- 可从仓库构建基础索引
- 可按关键词找到相关代码块

## P0-8 AI 分析任务执行

### 目标

基于异常组发起一次有证据的本地 AI 分析。

### 小需求

1. 从异常组提取代表日志和上下文
2. 检索相关代码 chunk
3. 组装 RAG Prompt
4. 调用 AI API
5. 保存分析报告

### 报告最小结构

- 问题摘要
- 证据链
- 根因猜测
- 影响范围
- 修复建议

### 验收标准

- 用户点击后可触发分析
- 页面能查看 Markdown 报告
- 报告包含具体日志证据和代码位置

## P0-9 修复 Task 生成

### 目标

将分析报告转成可直接投喂 AI coding agent 的任务文档。

### 小需求

1. 定义统一任务模板
2. 从分析报告提取核心字段
3. 生成 Markdown 修复任务
4. 支持复制和导出

### 模板建议

- 背景问题
- 根因分析
- 修改目标
- 涉及文件
- 验证步骤
- 风险提示

### 验收标准

- 用户能一键生成任务
- 导出的 Markdown 内容结构完整
- 内容适合直接粘贴给 Cursor 或 Aider

## P1-1 手动重试与错误反馈

### 目标

降低首版因日志不规则导致的失败率。

### 小需求

1. 展示解析失败数量
2. 提供重新解析入口
3. 允许用户调整解析模式后重试

## P1-2 手动合并与拆分异常组

### 目标

提高聚合结果的可控性。

### 小需求

1. 选择多个异常组合并
2. 将样本从异常组拆分出来重新归类

## P1-3 历史问题召回

### 目标

让系统逐步积累个人故障知识库。

### 小需求

1. 存储历史分析报告
2. 根据新异常检索相似历史问题
3. 在 AI 分析时加入历史参考

## 推荐任务组织方式

建议按以下顺序建立 issue：

1. 基础骨架
2. 上传与解析
3. 聚合与展示
4. 仓库导入与索引
5. AI 分析
6. 修复 Task 导出

这样可以最快跑通第一条可验证主链路。
