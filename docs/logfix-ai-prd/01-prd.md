# LogFix AI PRD

## 1. 产品基本信息

- 产品名称：LogFix AI
- 产品定位：个人生产日志智能排查与修复助手
- 当前版本：1.0 草稿整理版
- 文档日期：2026-04-08
- 目标用户：个人开发者、独立运维者、小型项目维护者

## 2. 产品背景

个人项目或小型生产环境中的日志问题排查通常具备以下特点：

- 日志来源零散，格式不统一
- 出错时缺少集中分析工具
- 传统可观测性平台部署成本过高
- 纯 LLM 分析缺少代码上下文，容易出现幻觉
- 修复建议难以直接转化为 AI coding agent 可执行输入

因此，需要一个轻量、本地优先、具备代码上下文能力的日志分析工具，将“日志排查”与“修复任务生成”连接起来。

## 3. 产品愿景

LogFix AI 旨在帮助个人开发者以最低的部署和使用成本，完成以下闭环：

`上传日志 -> 自动解析 -> 聚合异常 -> 关联代码 -> AI 根因分析 -> 生成修复任务`

该工具应满足以下原则：

- 默认轻量部署，尽量减少本地基础设施依赖
- 首版优先接入 AI API，而非本地模型运行时
- 足够轻量，普通开发机即可运行
- 结果结构化，可直接服务于后续代码修复
- 面向个人场景，而不是企业级 observability 平台

## 4. 产品目标

### 4.1 核心目标

- 降低个人项目生产故障的平均排查与修复时间
- 将日志分析结果与本地代码仓库关联，减少 LLM 幻觉
- 生成可直接交给 Cursor、Aider、Continue.dev 等工具的修复任务

### 4.2 MVP 成功指标

- 支持上传并成功解析常见日志文件
- 能将同类异常聚合为异常组
- AI 报告中包含日志证据和代码指向
- 能导出一份可用的 Markdown 修复任务
- 在个人电脑上可顺畅运行，非模型占用控制在 2GB RAM 内
- 单次典型排查流程可在 5 分钟内完成

## 5. 用户画像

### 5.1 目标用户

- 独立开发者
- 个人 SaaS 或副业项目维护者
- 偶尔处理线上问题的全栈开发者

### 5.2 用户特征

- 熟悉 Python、JavaScript 或常见 Web 技术栈
- 有本地 Git 仓库
- 能接受安装 Ollama 与本地模型
- 更关心效率和隐私，而不是复杂平台能力

## 6. 核心使用场景

### 6.1 事后排查

用户在服务异常后，导出生产日志并上传，系统自动解析、聚合并生成 AI 根因分析报告。

### 6.2 代码上下文增强

用户选择本地代码仓库目录后，系统对代码建立索引，后续分析可引用相关文件、函数和模块。

### 6.3 日常维护

用户持续使用时，可以逐步积累历史异常记录，用于相似问题召回与对比。

### 6.4 修复闭环

用户基于 AI 报告一键生成修复任务，复制给 AI coding agent 执行代码修复，并重新导入日志验证结果。

## 7. 功能范围

### 7.1 日志摄入与解析

支持用户通过 Web 页面上传日志文件。

需求包括：

- 支持拖拽上传和文件选择上传
- 支持文件类型：`.log`、`.txt`、`.json`、`.zip`
- 支持多文件批量上传
- 对日志进行结构化解析，尽量提取以下字段：
  - `timestamp`
  - `level`
  - `service` 或 `module`
  - `message`
  - `stack_trace`
  - `trace_id`
- 解析策略采用“规则优先 + LLM 补充”模式
- 解析结果落库，供后续聚合、展示和分析使用

### 7.2 异常聚合与汇总

系统应根据日志内容将相似错误归并为异常组。

需求包括：

- 基于 message 相似度和 stack trace 生成错误指纹
- 展示每个异常组的出现次数、时间范围、代表样本、严重等级
- 支持后续手动合并和拆分异常组
- 聚合结果存入 SQLite，支持筛选和排序

### 7.3 代码仓库集成

系统需要支持导入代码仓库，为 AI 分析提供代码上下文。

需求包括：

- 支持选择本地仓库目录
- 读取本地代码文件并建立基础索引
- 首版以文件级检索为主，可后续补充函数级切分
- 首版优先关键词检索，不强依赖 embedding 和向量库
- 最多支持 1 到 3 个仓库即可满足个人场景

### 7.4 可视化界面

系统需要提供简洁的 Web UI。

MVP 页面包括：

- 日志上传页
- 异常列表页
- 异常详情页
- AI 分析报告页

MVP 展示能力包括：

- 按时间、级别、服务筛选
- 搜索异常组
- 查看样本日志
- 查看时间范围和出现次数
- 触发 AI 分析

### 7.5 AI 智能分析

系统基于日志证据和代码上下文，生成根因分析报告。

需求包括：

- 基于异常组检索相关日志样本
- 检索相关代码片段或文件
- 可选检索历史相似异常
- 优先调用外部 AI API 进行分析
- 输出 Markdown 报告，至少包含：
  - 问题摘要
  - 证据链
  - 可能根因
  - 影响范围
  - 修复建议

### 7.6 修复任务生成

系统应将 AI 报告转成结构化修复任务，便于直接交给 AI coding agent。

输出至少包含：

- 问题定位
- 根因分析
- 建议修改点
- 测试验证步骤
- 风险提示

格式要求：

- 默认输出 Markdown
- 可附带 YAML 元数据
- 支持复制和导出

## 8. 非功能需求

### 8.1 部署与运行

- 支持本地 Python 直接运行
- 可后续补充 Docker 部署
- 默认数据和中间产物本地存储

### 8.2 技术约束

- 后端优先使用 FastAPI
- 前端优先使用 FastAPI 服务端页面方案
- 主数据库使用 SQLite
- 首版不强依赖向量数据库
- 模型调用优先使用 AI API
- 保留后续接入本地模型的扩展能力

### 8.3 性能要求

- 单次上传 10MB 以内日志解析和聚合应控制在 30 秒内
- 单次 AI 分析应尽量控制在 2 分钟内
- 支持几万条日志规模的查询和展示

### 8.4 安全与隐私

- 默认允许调用配置好的 AI API
- 除 AI API 外，尽量减少额外网络依赖
- 可选日志脱敏
- API Key 通过环境变量或本地配置文件注入

### 8.5 可用性

- 操作路径尽量少
- 错误提示清晰
- 解析失败时可重试
- 首版界面优先信息清晰，而非复杂交互

## 9. MVP 范围

MVP 必做项：

- 日志上传与解析
- SQLite 持久化
- 基础异常聚合
- 异常列表和详情页
- 本地仓库目录接入与基础索引
- AI 根因分析报告
- 修复任务 Markdown 生成

MVP 暂不包含：

- 实时日志接入
- 多人协作
- 企业级权限系统
- 告警通知
- 自动修复执行

## 10. 假设、风险与依赖

### 10.1 假设

- 用户可提供本地代码仓库目录
- 用户可配置可用的 AI API
- 用户日志量级为个人项目规模

### 10.2 风险

- 日志格式不规则导致解析不稳定
- 关键词检索精度不足导致代码召回效果一般
- AI API 成本、延迟或配额影响体验

### 10.3 应对策略

- 规则解析优先，LLM 作为补充而不是主路径
- 先做文件级检索，必要时再补函数级切分
- 对 AI 报告强制输出证据链，减少无依据结论

## 11. 产品结论

LogFix AI 的本质不是“又一个日志平台”，而是一个面向个人开发者的本地 AI 排障工作台。MVP 阶段应坚持两个原则：

- 先打通闭环，不追求企业级能力
- 先保证证据链和结果可执行，再追求高级智能化
