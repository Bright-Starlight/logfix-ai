# cilipa 宪法

## 核心原则

### I. 规范驱动开发

每个功能都必须从完整的规格说明开始。功能规格必须包含可独立测试的用户场景，
并且规格必须在编码前获得批准。理由：防止对错误实现浪费精力，并提供明确的验收标准。

### II. TDD（测试驱动开发）（不可妥协）

代码开发必须遵循 TDD。必须先写测试，测试必须初始失败，实现后测试通过，
并严格遵循 Red-Green-Refactor 循环。理由：确保可测试性、防止回归，
并在假设之前完成验证。

### III. 增量交付

功能必须能够以独立增量方式交付。每个用户故事必须可独立测试和部署，
并且必须遵循 MVP 优先原则，先实现最简可行方案。理由：降低风险、
提前获得反馈，并防止过度设计。

### IV. 代码质量

代码必须清晰、可读、命名良好。函数应小于 50 行，文件应专注于单一目的并控制在
800 行以内。优先使用不可变性；可变操作必须明确且受控。错误必须在每一层全面处理。
必须保留有意义的注释，不得随意删除注释。理由：提升可维护性、可调试性并减少副作用。

### V. 可观测性

所有重要操作都必须通过结构化日志实现可观测。必须使用日志框架
进行日志记录。

**日志输出要求**：
- 日志文件必须输出到 `/log` 目录下。
- 日志文件命名规范必须为 `{项目名}_{日期}.log`，例如 `logfix-ai_20260407.log`。
- 控制台（stdout/stderr）仅用于人类可读的进度输出。

**代码关键位置必须输出日志**，包括但不限于：
- 外部 API 或网络请求的输入和输出，例如请求参数、响应状态。
- 关键业务逻辑的分支判断，例如条件选择、筛选结果。
- 状态变更和转换，例如处理开始、处理结束、结果选择。
- 异常和错误处理，例如错误原因、恢复动作。

**日志格式要求**：
- 必须使用标准日志级别：`DEBUG`、`INFO`、`WARNING`、`ERROR`。
- 日志内容必须包含关键上下文数据，例如关键词、处理结果、文件路径。
- 必须避免日志冗余；同类操作应优先使用结构化批量输出。

理由：支持生产环境调试、事件响应和性能分析，日志文件便于离线排查问题。

### VI. 文档语言

项目所有文档正文内容必须使用中文编写。模板标题可保留英文作为标准化标记，
但生成的规格说明、计划文档等正文必须使用中文。所有完成后的报告、总结、审查意见、
测试报告也必须使用中文。理由：确保团队成员可理解项目文档，
避免语言障碍导致误解。

### VII. 代码执行流程图

在 `/speckit.tasks` 阶段，必须先绘制代码执行流程图并保存到
`specs/###-feature-name/flow.md`，且必须使用 Mermaid 语法。
流程图中的所有文字内容必须使用中文编写，包括节点描述、状态名称、函数说明等。
理由：在实现前明确运行时事件流和数据流，减少返工并提升沟通效率。

### VIII. 集成验证

在 `/speckit.implement` 完成后，必须验证功能已正确集成到主应用中，而不是仅完成独立模块开发。

1. **代码层面验证（必须）**：必须直接阅读代码并确认以下内容：
   - 组件是否已导入到主应用。
   - 组件是否正确渲染并传递正确的 props。
   - Store 状态是否正确连接。
   - 用户可见功能入口是否存在。
   - UI 组件是否实际使用了 store 中的数据。
2. **清单文件验证（辅助）**：可以检查清单文件的完成状态，但不得替代代码验证。

验证必须通过阅读代码确认，而非仅依赖清单文件打勾。理由：防止功能完成后因未集成
而导致用户无法使用。

3. **测试验证（必须）**：`/speckit.implement` 完成后必须执行以下测试：
   - 运行项目测试套件：`pytest`（后端）、`vitest`（前端）
   - 使用 `/webapp-testing` 进行 E2E 页面测试，验证 UI 功能和用户流程
   - 性能测试任务（Phase 11 中的 T072.5、T072.6、T072.7）必须在此时执行

4. **代码审核（必须）**：`/speckit.implement` 完成后必须执行代码审核：
   - 使用 `/rsmdt-the-startup-code-quality-review` 进行代码质量审核
   - 审核必须在测试之前进行
   - 审核发现的问题必须修复后才能继续

理由：确保实现功能正确且页面可正常访问，防止集成问题遗留到生产环境。

## 附加约束

### 安全要求

- 不得硬编码密钥、密码或令牌，必须使用环境变量或密钥管理器。
- 所有用户输入都必须在处理前验证。
- 遇到无效输入时必须快速失败并给出清晰错误信息。
- 理由：防止凭证泄露和注入攻击。

### 数据库规范

- **所有数据表必须包含表注释**（`__table_args__ = {"comment": "表描述"}`），注释内容不得为空。
- **所有字段必须包含字段注释**（`comment="字段描述"`），注释内容不得为空。
- **主键 ID 必须使用 Long 类型**（SQLAlchemy 中使用 `BigInteger`），**严格禁止使用 UUID**。
- 外键关联字段应在注释中说明关联关系和级联规则。
- 枚举类型字段应在注释中说明各枚举值的含义。
- 理由：确保数据库结构可维护、可理解，Long 类型主键更紧凑、顺序性好、利于分库分表。

### Windows 环境

当前开发环境为 Windows。代码和脚本必须兼容 Windows 平台。理由：确保开发人员在
Windows 环境下正常工作，所有工具链和脚本都必须可执行。

## 开发工作流

### 流程要求

1. **先研究**：编码前必须先搜索现有实现、模板和模式。
2. **先计划**：编码前必须创建并审查实施计划。
3. **先测试**：实现前必须依据 TDD 原则先编写失败测试。
4. **代码审查**：所有变更在合并前必须审查，审查者必须验证宪法合规性。
5. **宪法合规**：所有 PR 和审查都必须验证对本宪法的遵循；若偏离原则，必须在计划文档中说明理由。

### 质量门禁

- 功能实现仅在规格批准后开始。
- 用户故事实现仅在基础阶段完成后开始。
- 测试必须通过后方可合并。
- 计划模板中的宪法检查必须在 0 阶段研究开始前通过。

## 治理

本宪法优先于所有其他开发实践。修正必须遵循以下程序：

1. 提议的变更必须记录理由和迁移计划。
2. 变更必须通过与代码变更相同的审查流程批准。
3. 版本号必须遵循语义化版本规则递增：
   - `MAJOR`：向后不兼容的治理变更、原则移除或重新定义。
   - `MINOR`：新增原则、新章节或实质性扩展的指导。
   - `PATCH`：澄清、措辞修正、错别字修正、非语义性改进。

所有 PR、计划审查和实现审查都必须包含宪法合规检查结果。
